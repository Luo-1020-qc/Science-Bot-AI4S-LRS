## 1. 判断与项目定位

**这个框架适合成为我们的评测主干。它让“科研 Agent 完成了任务”变成可检查的执行事实，尤其适合观察理解用户、保留目标、正确调用工具和按依赖完成流程的能力。科研方法的适用性、结论有效性和真实复现质量，还需要领域验收器。**

论文贡献是评测方法和数据集，并未提出或验证一种解决这些问题的新规划/RL 算法。因此，“完全基于新方法”应落实为重新组织任务、对话、状态环境、执行日志和独立评分；改进 Agent 的方式仍是待比较的实验变量。

项目当前路线已从“二次曲面 + LangGraph + RL”调整为 OpenCode 高层交互、可执行科研服务和经验复用。RUT 是这条路线的评价层，能够接在不同规划器之外，不需要将 OpenCode 改造成一个新的双重自主规划系统。

## 3. 官方代码口径需要补充说明

2026-10-12 查阅的官方 `eval/completion.py` 使用 `gold_action_graph` 中的必要读等价集合、必要写节点、参数匹配与动作级依赖，并检查终态断言、状态差异、澄清/拒绝和禁止动作。[官方 completion.py](https://github.com/Miaow-Lab/RUT-Bench/blob/main/eval/completion.py)

同日查阅的 `eval/run_eval.py` 在汇总时以 `relaxed_success` 计算 `success_rate`，并保留严格指标；较宽松判定侧重终态和禁止动作。**论文正文的三项成功定义与当前主分数汇总代码之间存在口径差异。** 不能据此推断论文中每个报告数字究竟由哪个历史版本产生。[官方 run_eval.py](https://github.com/Miaow-Lab/RUT-Bench/blob/main/eval/run_eval.py)

本项目固定 `execution_success` 为主指标，额外输出 `state_only_success_extension`，用于发现“最终结果对了，但中间顺序/参数不合规”的情况。后者包含本项目的科学检查，并不是官方 relaxed 分数的逐项复现。官方复现阶段需要固定提交、数据与汇总脚本，再重新跑通。

## 4. 从框架到实现需要收紧的地方

### 4.1 轨迹匹配必须绑定对象

“检查了某个数据集”不等于“检查了随后训练的那个数据集”。工具名级 `first_pos` 无法处理对象混淆、重复调用或失败后修复。

首版 Gold Action 使用节点 ID、工具名、参数及工具返回 ID 的引用，例如 `$inspect.dataset_id`。匹配只接受成功调用；一个实际调用只能覆盖一个必要节点。依赖图作用于节点，早先失败的前置违规和禁止尝试保留在日志中，之后成功不能擦除。

首版只支持这一固定研究流程，未实现任意等价计划搜索、并行分支或多模型研究路径；扩展时新增可接受动作集合与有效性规则，不能简单取消动作覆盖。

### 4.2 矛盾请求需按是否可恢复拆开

配对核心采用两轮：第一轮出现训练限制或冲突，第二轮明确允许训练并恢复原始研究目标。所有变体最终按同一个协议和 Gold 终态评价，第一轮均不允许研究写入。这是项目定义的交互协议。

如果“禁止训练但要求新模型真实结果”的冲突没有被解除，正确结果是指出冲突并请求选择。此类样本进入 `response_only`，以交互成功单独统计，不能加入执行 SR 或配对 Gap 的分母。没有上下文又缺数据/目标的请求也进入该集合。

响应型评分器目前用有限中文术语、提问形式、响应类型和无写入事实判定；只能验证当前样本，不是通用语义 Judge。正式研究应增加盲审或独立 Judge，并审查无意义追问、错误对象和空泛拒绝。

### 4.3 科研成功不能由几个布尔标志代替

首版实际执行训练/验证/测试划分、训练均值或线性基线、计算独立测试 MAE，并生成溯源报告。评分器检查划分是否互斥、拟合行是否仅来自训练集、数据是否被修改，以及从模型系数和私有测试行重新计算的 MAE 是否匹配报告。

这验证一个合成数据上的 ML 工作流，不证明真实材料性质预测能力，也不构成整篇论文复现。真实复现任务还需要冻结参考代码、数据哈希、特征、划分、单位、允许修复与容差。

### 4.4 测试反馈必须保持边界

最新提案要求最终盲测不成为策略调参反馈。科研工具中的 `evaluate_model` 仅返回封存记录 ID；测试值写入评测端可见的最终报告，Agent 运行期间不会收到数值或预测。封存后拒绝再次划分、训练或评价。

真正面向用户交付报告时，在任务结束、策略冻结后通过受控产物入口读取报告；当前 MVP 将报告保存在 episode 的 `final_state.reports`。这种进程内工具边界不等于恶意代码的操作系统隔离，后续接 OpenCode 文件/命令工具时必须使用单独工作区与服务权限。

## 5. 新的实施顺序

1. **先固定评分器。** 构建状态沙箱、任务 Oracle、三项硬评分和反例，让目标是否完成有可信答案。
2. **再固定配对测试。** 同任务、同快照、同科学协议，仅变用户行为；先验证 5 × 7 的开发集合。
3. **再测真实 Agent。** 同一模型、工具、步数、时间和上下文上限，比较普通工具循环、澄清策略、显式依赖规划；API 模型与规则控制分开报告。
4. **再接我们的入口。** OpenCode/MCP 与 SciencePal 的适配层共用服务端任务状态和评分器，保留真实执行证据。
5. **最后研究学习。** 根据失败归因选择一个受限修复/调度问题；先做规则和监督基线，再决定 bandit 或 RL。测试期间冻结技能库和策略，测试反馈不进入训练。

| 待检验改进 | 最有解释力的 RUT 诊断 | 需要额外排除的解释 |
|---|---|---|
| 上下文保持与必要澄清 | Underspecification；R1a/R1b | 是否额外给了答案或未来对话 |
| 显式 DAG 与动作校验 | R2；依赖违规 | 是否工具层已强制修复所有错误 |
| 可执行技能与专家检索 | R3、失败调用、总成本 | 是否换了更强模型或增加预算 |
| 轻量修复策略学习 | 故障扩展的恢复成功、成本 | 是否记住开发任务；是否优化盲测反馈 |

## 6. 当前交付与证据范围

已交付：独立 Python 包、一个 Scientific ML 环境、5 个任务、35 个两轮配对实例、每任务 2 个响应型实例、3 个离线协议控制器、可选 HTTP JSON 模型适配器、日志、分组成功率、配对 Gap、根任务 bootstrap、五类失败检测与自动测试。

离线运行覆盖 3 个控制器 × 3 个种子 × (35 个核心 + 10 个响应型) = **405 次 episode**。这些控制器按公开协议解析固定样本，100% 成功表示环境与执行循环可达；仅看最后一轮的控制器在上下文缺失变体失败是预设的机制检查。它们不能支持“显式规划提升了 LLM”的研究结论。

上述为 v0.1 初始交付范围。后续已完成真实模型开发评测、公开 Darcy CPU 后端和 v0.4 结构化规划；v0.5 进一步实现终端科研交互、规格确认、双候选验证集选择与有界原子恢复，见 [交互与恢复契约](Research_Interaction_and_Recovery_zh.md)。这些工程结果仍不构成官方 RUT 数值复现、真实材料实验或规划增益证据；OpenCode/MCP、SciencePal、动态目标、RL 和正式留出评测尚待完成。

详细工程阶段、验收条件和运行命令见 [新实施方案](../../Markdown%20Document/Scientific_Agent_RL_Planning_Implementation_Plan.md) 与 [代码 README](../README.md)。
