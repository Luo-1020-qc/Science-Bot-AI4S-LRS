# science Bot 通用科研 Agent 改造方案

日期：2026-10-21。性质：下一阶段设计与验收建议，尚未实现。本方案不更改运行代码、不重新训练权重、不产生真实 API 调用。保持现有 `science-bot.cmd` 入口，交付采用源码、文档与增量验收记录，不新增 ZIP。

> 2026-10-22 进展：G1 已按独立 `general_v1` 会话接入，G2 已接入三个受限表格任务族与版本化设计/计划协议。当前行为及限制见 [G2 使用说明](Science_Bot_G2_表格与实验设计_zh.md) 与 [G1 使用说明](Science_Bot_G1_通用入口_zh.md)，验收分别在 `delivery/g2_update/` 和 `delivery/g1_update/`。下文保留原设计快照，G3/G4 尚未实施；G2 不代表任意统计设计均可执行。

## 目标与第一批场景

目标是同一入口理解不同任务、发现适用工具、形成可检查的实验设计、执行并根据证据调整计划。每个新领域通过工具和领域契约接入；新增领域无需重写整个 Agent。

第一批建议覆盖三个能力层次：

1. 项目文件问答：找到相关文件、读取明确选择的片段、引用来源回答；不触发实验。
2. 表格数据与统计实验：检查 CSV、识别变量和数据来源、提出适合问题的设计与分析、执行已注册数值工具。
3. 数值科研：复用 generated / Darcy，随后单独接入 CViT 的配置化训练与评价入口。

第 3 项的 CViT 适配应先盘点现有脚本接口、数据、依赖和 GPU 开销，再决定第一版可执行范围。不能将“读取 dynamic_cvit.py”作为训练已接入的证据。

## 当前需要拆开的固定结构

| 位置 | 当前限制 | 改动方向 |
|---|---|---|
| `science_bot/session.py` | 创建会话即创建默认研究规格和数值环境 | 新会话先保存消息、工作区和意图；确认具体研究后才创建领域环境 |
| `science_bot/contracts.py` | generated / darcy、固定 mean/ridge 目录 | 保留旧协议，另建可扩展工具注册表与任务/实验协议 |
| `science_bot/llm.py`、`agents.py` | 四种固定 JSON 角色，适配器未读取原生 tool_calls | 添加工具调用适配器与通用消息循环，保留原有账本及模型输出展示 |
| `science_bot/graph.py` | 固定候选行动循环 | 顶层增加任务路由、工具检索、计划校验、观察和局部重规划 |
| `plan_spec.py` | v1 限定六节点、固定工具集合 | 建立新的通用执行计划协议；通过适配器复用旧执行器 |
| `science_bot/policies.py` | 固定行动类别和 24 槽特征协议 | 旧 RL 只用于匹配场景；通用路径先建立 LLM 与规则基线 |

不扩大旧枚举来冒充通用化，也不直接把旧 checkpoint 用于新的工具类型。通用层和旧科研引擎采用独立版本，新会话记录引擎版本，恢复时按原版本读取。

## 建议结构

```text
science_bot/
  general/
    contracts.py           # TaskRequest、ToolSpec、ExperimentSpec、ExecutionPlan
    conversation.py        # 消息与上下文，不预建默认科研环境
    router.py              # 回答 / 项目问答 / 分析 / 设计 / 执行 / 澄清
    registry.py            # 注册工具、领域适配器、按任务筛选工具
    planner.py             # LLM 计划与局部修订
    validator.py           # 结构、语义、资源、依赖及领域检查
    executor.py            # 共享执行、幂等、作业对账与证据
    graph.py               # 通用 LangGraph 状态循环
    adapters/
      legacy_numeric.py    # 原 generated / Darcy 与旧策略
      tabular.py           # 表格数据与统计分析
      project_qa.py        # 显式上下文选择、带文件引用的回答
      cvit.py              # 后续注册训练入口，不是任意 shell
```

这是建议的模块边界；实现时应复用已有工作区、预算、作业登记、输出展示与 SQLite checkpoint，避免产生第二套不一致的账本。图状态保存引用和执行位置，科研账本保存实际证据。

## 任务理解与工具调用

`TaskRequest` 应包含用户原始需求、意图、领域、输入引用、目标、约束、缺项和字段来源。缺少关键输入时澄清；不支持的任务显式指出缺少哪个工具。未识别的任务不继承 generated 默认值，也不在用户确认旧默认值后声称完成新任务。

问答和计划讨论不自动授权训练。用户已经明确授权的工具操作继续执行；更换数据身份、增加预算或越出确认范围时才重新确认。研究计划应先具体化到可检查的工具、参数与开销。

每个 `ToolSpec` 包含：名称、用途、适用领域、输入/输出 schema、对象引用类型、前置条件、资源估算、读写作用、幂等/重试方式和结果核验器。工具说明应包含适用与不适用的例子。

工具集合根据任务、输入类型与当前状态筛选；LLM 提出调用，宿主再核对工具是否注册、参数与输入身份、前置条件、预算与授权范围。工具输出写入证据索引，再由规划器决定继续、修复或结束。模型不能通过工具返回中的文字获得额外权限。

建议为当前模型服务补充原生 tool_calls 支持，保存 tool_call_id、结构化参数、工具结果与请求用量。旧 JSON 提案仍可作为显式兼容路径，但两种路径都必须进入同一宿主校验和执行层。原生格式不会替代业务正确性检查。

官方依据：LangChain 工具使用明确 schema 和用途描述；DeepSeek 工具调用由模型提出函数请求，具体函数由宿主执行。[Tools](https://docs.langchain.com/oss/python/langchain/tools)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)。接入时对已锁定依赖和实际供应商端点做兼容测试，不自动升级依赖或切换端点。

## 实验设计协议

建立独立 `ExperimentSpec`，至少表达以下内容；按场景决定哪些字段必填或不适用，不能让模型补造缺失的科学依据。

- 研究问题、可检验假设、目标是预测比较还是因果效应。
- 数据/样本来源、实验单位、输入身份和数据限制。
- 因素、水平、响应变量、控制条件、基线与比较方法。
- 随机化、区组、重复方式；区分随机种子重复和独立实验单位。
- 数据划分、预处理拟合范围、评价指标、分析方法与不确定性报告。
- 样本/实验数的依据、时间与硬件预算、终止条件和失败处理。
- 验证数据如何指导迭代、最终评价何时冻结、哪些结论不能支持。

例如，比较两个训练配置需要控制数据划分与训练预算，设计配对重复，并报告差值及不确定性；分析观察性 CSV 时不能仅凭显著性宣称因果。样本不足或关键设计信息缺失时，输出有条件的方案与待补信息。

`ExecutionPlan` 则表达工具节点、参数/产物引用、依赖、资源、检查条件和版本。实验设计与执行步骤分别验收。允许修订未执行节点，保留旧版本和已完成证据；测试结果不反馈给参数搜索。

## LangGraph 循环

```text
理解任务 → 路由 → 获取必要上下文 → 发现工具
    ├─ 问答：调用必要只读工具 → 带证据回答
    ├─ 设计：生成实验设计 → 校验 → 展示方案
    └─ 执行：明确规格/范围 → 形成计划 → 校验 → 执行一个就绪步骤
                                                   ↓
                                      观察结果 → 局部重规划 / 结束
```

已有 checkpoint、进程锁、预算、幂等和作业对账继续使用。外部训练进程要新增启动登记、资源占用、日志位置、轮询与退出码，不把图恢复等同于任意外部作业自动恢复。

LangGraph 官方区分固定工作流与动态工具决策，并提供持久化机制；本方案选择将确定性的执行约束与动态规划结合，而非替换整个框架。[Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

## 分阶段交付

| 阶段 | 交付 | 核心验收 |
|---|---|---|
| G1 通用入口与工具内核 | 意图分流、工具注册、模型调用适配、旧科研引擎适配；项目文件问答和原数值实验跑通 | 同一入口正确处理问答、澄清和实验；未知任务不触发默认实验；不重复调用；模型回看可用 |
| G2 表格与实验设计 | CSV 工具、ExperimentSpec、设计检查与通用计划执行 | 在新数据上提出并执行适合问题的比较；数据隔离、参数与指标可重算；缺项会澄清 |
| G3 CViT 真实工作流 | 配置化训练、资源估算、任务登记、训练评估与产物验收 | 使用真实训练与输出，无模型编造结果；暂停后对账，不盲目重复 GPU 作业 |
| G4 泛化与学习研究 | 领域留出、工具组合留出、公平 LLM/规则/学习策略比较 | 报告成功率、设计有效性、恢复、耗时、token 和计算成本；有证据后决定是否训练新策略 |

首轮建议完成 G1，并为 G2 冻结协议和小型任务集。G1 不应宣称已具备完整通用实验设计；G2 必须加入真正不同于旧回归目录的任务族。

## 如何检验“准确”

分别统计任务路由、应调用/不应调用、工具选择、参数语义、调用依赖、实验设计有效性、数值结果与最终交付。JSON 合法率单独报告，不能代替整体正确率。

按数据来源和任务族划分开发与留出；同任务换措辞不能计为新的独立科研任务。包含澄清、工具选择干扰项、缺失数据、无效参数、重复请求、部分失败、预算不足与不应执行的问答任务。自动断言结合领域设计规则；实验设计的复杂语义可人工审查，不单独依赖同一 LLM 自评。

对比当前固定版本和通用版本，固定模型、资源和工具可用性。尚未建立基准前不承诺“所有场景准确”或预设性能增益。现有 RL 在受控试验中未证明优于强规则，优先完善通用工具闭环及其证据，再决定训练目标。
